# Release notes

## 0.2.0 — the first public release

`uvp-agents` 0.2.0 was tagged and published on 2026-10-17. It is the first
version on npm's `latest` tag and the first GitHub release
([tag `uvp-agents-0.2.0`](https://github.com/Antruly/uvp/releases/tag/uvp-agents-0.2.0)).
The tag and the npm upload are separate events: the GitHub release was published
at 12:13Z, and the manual npm publish completed at 13:22Z.

This page is the reader-facing summary. The
[changelog](https://github.com/Antruly/uvp/blob/main/CHANGELOG.md) is the complete
generated record, and later versions add their own sections there.

### What uvp is

uvp generates, builds, runs, and verifies C++ web services that link against
[libuvcpp](https://github.com/Antruly/libuvcpp). The generated project is an
ordinary CMake project: it builds with plain CMake against an installed
libuvcpp, carries no uvp runtime dependency, and stays usable after you stop
using uvp.

It is not a C++ framework you link, a production deployment or scaling tool, or
a sandbox. Generated services run with your permissions on your machine.

### What ships

- **Six templates:** `hello-http`, `rest-api`, `websocket-echo`, `soap-service`,
  `static-files`, and `http3-service`.
- **15 MCP tools** over the same contracts as the CLI. The generated catalog is
  [the MCP contracts page](mcp-contracts.md) and
  `docs/public/tool-catalog.json` in the package.
- **The evidence model:** every report separates observed, derived, unknown, and
  undetermined outcomes instead of collapsing them into a pass or a refusal. See
  [the evidence model](evidence.md).
- **The web toolbox:** HTTP and SOAP calls, a WebSocket probe on Node and
  libuvcpp's own client stack, capture and replay, and load timings with
  percentiles.
- **Two toolchain providers:** `local` is exercised end to end on Linux and
  Windows. `container` is implemented and tested against an image you supply;
  no CI lane exercises it. `remote-ssh` is not written.
- **A Windows MSVC lane:** six generated workspaces built and run under the
  installed Visual Studio, through both Ninja and the default Visual Studio
  generator.

The exact platform, compiler, generator, feature, dialect, and provider coverage
is in the [first-release support matrix](support-matrix.md), with the run and job
behind each row.

### Install and connect

```bash
npm install --global uvp-agents
uvp --version
uvp doctor
```

`npx uvp-agents doctor` runs without installing. The requirements are Node
`^22.19.0`, `^24.11.0`, or `>=26.0.0`; CMake 3.20 or newer; a C++14 compiler; and
**libuvcpp 1.7.0 or newer**, either from a CMake install or a prebuilt release
archive through `pkg-config`. [Installation](installation.md) covers both discovery
routes.

Connect an MCP client:

```bash
# Claude Code
claude mcp add uvp -- npx -y uvp-agents mcp
```

For Claude Desktop, Cursor, and other stdio clients, use the same command in the
client's JSON configuration:

```json
{
  "mcpServers": {
    "uvp": {
      "command": "npx",
      "args": ["-y", "uvp-agents", "mcp"]
    }
  }
}
```

### Upgrade guidance

uvp is pre-1.0, and the compatibility promise in
[Releasing](releasing.md#compatibility-promises) is deliberately narrow:

- **Tool contracts are stable.** A change to an existing tool's input or output
  schema is a breaking change and is marked in the changelog, because an agent
  that cached a schema must keep working.
- **Generated code is not byte-stable.** A new uvp version may emit different
  C++, and a workspace generated by an older version is not expected to be
  regenerable byte-for-byte by a newer one.
- **The libuvcpp floor is 1.7.0.** uvp will not require a newer libuvcpp within a
  minor series without saying so.

The changelog marks the following changes as breaking relative to the `0.1.0`
tree. That tree was never published, so they matter to readers of pre-release
snapshots and to clients that cached an earlier schema; they are also the
vocabulary the first release uses.

- **`toolchain` is honoured.** A `uvp.json` that already carried a `toolchain`
  field previously had it ignored; it now changes where the workspace is built,
  and `uvp_verify` refuses the workspace until the call passes
  `toolchain: "local"`.
- **`uvp_assert_exchange` vocabulary.** The `passed`/`failed` counters are
  replaced by `satisfied`, `unmet`, and `undetermined`; `results[]` rows carry
  `status` instead of `passed`; `not_evaluated[]` is gone.
- **`uvp_soap_call` gains `max_body_bytes`.** The default is the previously
  fixed cap, so an existing call sends the same request; the input schema is
  closed, so a cached schema sees a new property.
- **Bodies carry exact bytes.** `base64` appears beside a lossy `text`, and
  `text_lossy` names when and why a text decoding is not the bytes. Both output
  schemas are closed, so a cached schema rejects the new fields.
- **TLS reports a third state.** `tls.verified` and `tls.errors` become
  `tls.verification` (`verified`, `failed`, `not_checked`, `undetermined`) and
  `tls.reason`. A certificate the client will not accept now exits 2 as
  `target_unavailable` and is not retryable.
- **`uvp_websocket_probe` does not always report a handshake.** On the native
  libuvcpp stack the C ABI does not report the upgrade response, so `handshake`
  is absent and `not_observable` names the other unfillable fields. The tool
  declares `spawnsProcess: true` unconditionally.
- **Capture errors are split.** `capture_unavailable` becomes
  `capture_listen_failed` and `capture_not_found`.

### Known limitations and unknowns

These are recorded as `unknown` in the [support matrix](support-matrix.md), not
as unsupported:

- macOS, Clang, and Visual Studio 2019 are not exercised by a CI lane. The
  README's MSVC 2019+ floor is inferred rather than observed. The Linux lane
  passes no `--generator`, so CMake's Unix Makefiles default is derived rather
  than named.
- HTTP/2 has no observed exchange. The Linux lane builds libuvcpp without
  nghttp2; the Windows archive enables it, but no lane asserts an HTTP/2 request.
- MySQL and PostgreSQL are not claimed: only the refusal path for a missing
  driver is exercised. SQLite is observed end to end.
- gRPC has no build switch in libuvcpp 1.7.0; only header existence is
  checkable.
- Windows builds and runs all six templates, but the native probe is not built
  there, so the HTTP/3 transport and libuvcpp's own WebSocket client exchange are
  unobserved on Windows. MSVC `LNK2019`/`LNK2001` link diagnostics are
  deliberately unmatched.
- The container provider is not exercised in CI; it needs a runtime and an image
  that is already present. `remote-ssh` is not written.

Release-process facts that affect what this version can claim:

- **0.2.0 has no npm provenance attestation.** It was the first publish, and
  trusted publishing requires an existing package, so the upload was manual. A
  manual publish cannot carry provenance.
- **Trusted publishing is not attached yet.** A dispatch of `publish.yml` fails
  at `npm publish` until it is, uploading nothing; later versions are meant to
  use that workflow, which has not been exercised.
- **The MCP registry entry is prepared and checked, not published here.**
  Publishing it is a separate maintainer action after the npm package exists;
  see [Releasing](releasing.md#publishing-the-mcp-registry-entry).
- **Release metadata is regenerated by hand on the release PR (Option B).** The
  release-please workflow does not take write access to a pull-request branch, so
  the maintainer runs `npm run docs:generate` and checks `npm run docs:check`
  before merging. If no CI run happens on the release PR, the stale
  `sbom.cdx.json` is caught by that manual check, not by a red check.
- `0.0.0-stage` also exists on npm, a staging upload from the same session.
  `latest` points at 0.2.0.
