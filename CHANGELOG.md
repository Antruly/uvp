## [0.2.0](https://github.com/Antruly/uvp/compare/uvp-agents-0.1.0...uvp-agents-0.2.0) (2026-10-17)


### ⚠ BREAKING CHANGES

* **toolchain:** a `uvp.json` that already carried a `toolchain` field was ignored before and is honoured now, so such a workspace changes where it is built. `uvp_verify` refuses one until the call passes `toolchain: "local"`.
* **web:** `uvp_assert_exchange`'s output replaces the `passed` and `failed` counters with `satisfied`, `unmet` and `undetermined`, drops `not_evaluated[]` in favour of rows carrying `status`, and replaces each `results[]` row's `passed: boolean` with `status: "satisfied" | "unmet" | "undetermined"`. The assertion engine's `AssertionOutcome` changes with it. `docs/public/tool-catalog.json` and the shipped skill are regenerated from the contracts.
* **soap:** `uvp_soap_call`'s input schema gains `max_body_bytes`. Nothing behind it breaks — the default is the number that was fixed before it, so a call a caller already writes sends the same request and gets a byte-identical answer — but a change to an existing tool's input schema is breaking by `docs/releasing.md`'s compatibility promise, and the reason is the reader it names: a client that cached the input schema and compares it against the catalog now finds a property its copy does not have, and a failed schema comparison has to be looked at whether or not anything broke behind it.
* **web:** `base64` appears beside a lossy `text` where it did not before, and on `uvp_soap_call`'s body the field is new. Both output schemas are closed (`additionalProperties: false`), so a client that cached the previous schema and validates against it rejects a body carrying a field that schema did not declare — the reader `docs/releasing.md` promises to keep working.
* **web:** `uvp_http_request` and `uvp_soap_call` gain `text_lossy` on their body object, optional, and it is breaking anyway: the catalog's objects carry `additionalProperties: false`, so a client that cached the previous output schema and validates against it rejects a body that now carries the field. That is the reader `docs/releasing.md` promises to keep working, which is why the commit is marked rather than filed as the additive change the shape of it suggests. A caller whose text is the bytes reads nothing new, which is the ordinary case; when it is not, the field names whether the peer's bytes or a cap of the caller's caused it.
* **tls:** `uvp_http_request`'s `tls` object no longer carries `verified` or `errors`. `verification` is one of `verified`, `failed`, `not_checked`, or `undetermined`, and `reason` carries the failing code when there is one. A caller reading `tls.verified` reads `tls.verification === "verified"`; a caller reading `tls.errors` reads `tls.reason`, which is present exactly when OpenSSL had something to say. A certificate this client will not accept now exits 2 as `target_unavailable` rather than 1 as `endpoint_unreachable`, and is no longer `retryable`.
* `uvp_websocket_probe` no longer always returns `handshake`. On the native stack it is absent, because the C ABI does not report the upgrade response; a caller that reads `handshake.status` must now handle its absence, which is a statement about the stack rather than a malformed result, and `not_observable` says which other fields the same stack cannot fill. The tool also declares `spawnsProcess: true` unconditionally — the effect set is a closed set of booleans and cannot express "only when `--stack libuvcpp` is used" — so a caller that treated this tool as one that runs nothing must not.
